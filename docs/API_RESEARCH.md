# Исследование API

Исследование выполнено 18 ноября 2026 года на
https://qa-desk.education-services.ru/.
Chrome уже был установлен. Использованы Google Chrome DevTools → Network,
публичный JavaScript фронтенда `main.672da7a6.js` и API-клиент на `requests`.
Документация или готовые чужие тесты для определения контракта не использовались.

## Как получены запросы

В новой вкладке Chrome открыт сервис, затем DevTools (`⌥⌘I` на macOS).
В Network включена запись и Keep log (в других версиях Chrome — Preserve log).
Через интерфейс выполнены регистрация, создание объявления, изменение названия,
удаление, повторная регистрация с тем же email и авторизация.
В каждом запросе изучены Headers, Payload и Response.

Исходный журнал экспортирован кнопкой Export HAR (sanitized).
В `frontend-traffic.redacted.har` оставлены шесть относящихся к заданию запросов;
дополнительно удалены JWT, пароли, cookies и служебные заголовки браузера.
Методы, URL, HTTP-статусы, поля запросов и ответы сохранены.
HAR можно импортировать в Chrome DevTools → Network → Import HAR.
Пароли и токены в нём заменены маркерами и для авторизации непригодны.

## Базовый адрес и авторизация

Базовый адрес: `https://qa-desk.education-services.ru/api`.
Защищённые запросы используют `Authorization: Bearer <token>`.
Регистрация и вход отправляют JSON. Создание и изменение объявления отправляют
`multipart/form-data`; boundary формирует HTTP-клиент автоматически.

### Регистрация — POST /signup

Тело, полученное из фронтенда:

```json
{
  "email": "sprint11.research.20261118.a92f@example.com",
  "password": "<test-password>",
  "submitPassword": "<test-password>"
}
```

Успешный ответ: `201 Created`. Поле `user` содержит `id`, `name`, `email`.
Токен расположен в `access_token.access_token`.

Повторный запрос с тем же email: `400 Bad Request`.

```json
{"statusCode": 400, "message": "Почта уже используется"}
```

В автотестах email создаётся заново для каждой регистрации нового пользователя.

### Авторизация — POST /signin

JSON содержит `email` и `password`. Успешный статус — **201**, что подтверждено
в Network. Ответ содержит `user` (`id`, `name`, `email`, `avatar`, `admin`) и
`token.access_token`. Путь к токену отличается от ответа регистрации.

### Создание — POST /create-listing

Multipart-поля: `name`, `category`, `condition`, `city`, `description`, `price`.
Исследован пример: категория `Авто`, состояние `Новый`, город `Москва`, цена `1000`.
Фронтенд позволяет создать объявление без фотографии.

Успешный ответ: `201 Created`, JSON самого объявления с полями `id`, `name`,
`category`, `condition`, `city`, `description`, числовым `price`, `owner`,
`createdAt`, `updatedAt`, `img1`, `img2`, `img3`, `isFavorite`.
В исследованном примере отсутствующие изображения и `isFavorite` равны `null`.

### Изменение — PATCH /update-offer/{id}

Фронтенд отправляет multipart с полным набором полей объявления и полями
`img1`, `img2`, `img3`. Для объявления без изображений значения этих трёх полей
передаются строками `null`. Тесты воспроизводят этот формат.
Успешный ответ: `200 OK`, JSON обновлённого объявления с прежними `id` и `owner`.

Редактирование чужого объявления через UI недоступно: фронтенд проверяет владельца.
Для проверки серверного ограничения тот же запрос воспроизведён API-клиентом
`requests` с токеном второго специально зарегистрированного пользователя.
Объявление принадлежало первому тестовому пользователю.
Фактический ответ: `401 Unauthorized`.

```json
{
  "message": "Оффер не найден или у вас нет прав на его редактирование",
  "error": "Unauthorized",
  "statusCode": 401
}
```

Автотест дополнительно читает объявление владельца и проверяет, что чужой запрос
не изменил ни одно проверяемое поле.

### Удаление — DELETE /listings/{id}

Тело запроса отсутствует. Успешный ответ: `200 OK`.

```json
{"message": "Объявление удалено успешно"}
```

В исследовательском API-запросе повторное удаление уже удалённого объявления
вернуло `500` с `{"statusCode":500,"message":"Internal server error"}`.
Это наблюдение вне обязательных сценариев; очистка тестов не выполняет повторное
удаление после успешного DELETE в тесте удаления.

### Чтение собственных объявлений — GET /profile/listings/{page}

Адрес найден в публичном JavaScript фронтенда, затем проверен запросом `requests`
под токеном владельца. Ответ `200 OK`:

```json
{"offers": [], "totalPages": 0}
```

Для пользователя с одним объявлением `offers` содержит его JSON, `totalPages`
равен `1`. Этот метод используется для проверки фактического создания,
сохранения изменений и удаления. У каждого теста новый владелец и максимум одно
объявление, поэтому данные других пользователей и пагинация не влияют на проверки.

## API-клиент

При исследовании через `requests.Session.request` передавались `json=payload`
для регистрации/входа, `files={field: (None, str(value))}` для multipart,
заголовок Bearer и таймаут. Статус и JSON изучались до написания проверок.
Эти вызовы оформлены в переиспользуемые методы модулей `api/user_api.py`
и `api/listing_api.py`.

Для повторного исследования в Postman можно создать запрос по указанному URL,
выбрать Body → raw → JSON либо Body → form-data, а для защищённых методов —
Authorization → Bearer Token. Email для новой регистрации нужно каждый раз
менять, токен брать из фактического ответа. Публичный сервис общий, поэтому
исследование выполнялось только на созданных для этой работы аккаунтах и объявлениях.
